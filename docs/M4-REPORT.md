## 四、这一轮抓到的关键缺陷

1. **url 制品的 sha256 被完全忽略**（Lead 验收时定位）
   `handleCreateArtifact` 的 JSON 分支只解 `{kind,url}`，`SHA256` 从未赋值 → **所有 url 制品发布必然失败**，部署功能等于不可用。修复：强制要求 sha256（缺失/非法 400，大写归一化），并把「sha256 是失败不破坏 current 的前提」写进代码注释。这是"M4 看起来做完了，但主路径根本走不通"的典型。

2. **retry 与收尾的丢唤醒竞态**（Lead 的 race 闸门发现，backend 修复）
   `Start` 在旧协程尚未从 `running` map 删除时静默忽略新请求；而 release 状态在删除之前就已写成终态。窗口内 retry → 有 run 永远停在 `pending` 且无人推进。这**不是数据竞争**（Go 检测器无告警），而是逻辑竞态——`-race` 只是变慢把窗口放大了。修复：改为「收尾后重跑队列」，保持「同一发布单执行协程」不变量。

3. **BSD `mv` 会跟随符号链接**（checkdev 实测发现）
   用 `mv` 切换 `current` 在 macOS 上会把新链接塞进旧 release 目录，**切换静默失败**（回滚就永远回错）。改用 `ln -sfn` + 真实目录先备份。这个坑在 Linux 上不会出现，属于"只在本机测才会撞到的平台差异"。

4. **回滚路径传空 Kind/Artifact**（checkdev 发现，backend 修）
   `rollbackOne` 调 `deploy.Build` 时传空结构体 → 回滚 API 必报错。而回滚是"出事了才用"的功能，最容易被测试漏掉。

5. **部署根重复拼 slug**（backend 自查）
   `Build` 内部会拼 `<Root>/<AppSlug>`，调用方又传了已含 slug 的路径 → `<root>/<slug>/<slug>`。已修正并加真实 `deploy.Build` 回归测试。

## 五、产品裁决（已写入契约）

| 事项 | 裁决 | 理由 |
|---|---|---|
| `app.root` 语义 | **基础目录**，实际路径 = `<root>/<slug>`；UI 需展示「实际部署路径」提示 | 与 `deploy.Build` 的 `BuildParams.Root` 一致；避免用户把 slug 也写进 root 造成双 slug |
| url 制品是否强制 sha256 | **强制**，登记时 fail-fast | 没有校验和就没有回滚保障；等到发布时才失败更难排查 |
| 模板占位符写法 | `{{APP_SLUG}}` 为准，兼容 `{{.APP_SLUG}}` | 原契约笔误，双写法成本极低 |
| agent 通道日志实时性 | 实时旁路 + 结束兜底（ssh 为步骤级实时） | 不自研完整流式下发器（等于复制 jobs 的 runID/等待表/超时/并发，风险高于收益） |

## 六、已知限制

1. **控制端重启后，pending/running 的发布不会自动恢复**（不续跑也不自动置失败），需 `retry` 或重发。已完成的服务器不受影响（`current` 原子切换不留半成品）。
2. **ssh 通道是步骤级实时**（命令结束才回传该步输出）；字节级实时需要 `sshx` 增加 `RunStream`，留待 M5。
3. `systemd` 模板需要目标机 root + systemd，`compose` 需要 docker；本机只能用 `binary` 模板做端到端验证，另外两类是结构断言。
4. 清理旧版本固定保留 5 个（`DefaultKeepReleases`），不可按应用配置。
5. 上传型制品需要 `LEADSTACK_PUBLIC_URL`（目标机要能回连控制端下载），不配时创建发布直接 400。
6. 告警列表与发布列表无分页；前端包体 620 kB（gzip 175 kB），未做路由懒加载。
7. 钉钉/飞书/Slack/Telegram 未对真实端点联网验证（离线无凭据）；Docker 镜像与 GoReleaser 仍只有结构校验。
